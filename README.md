# Прототип интеграции ПТО → Сметы → Снабжение

Работающий фрагмент сквозного процесса из тестового задания:

1. **ПТО** подаёт потребность в материалах.
2. **Сметный отдел** проверяет её и решает по каждой позиции, сколько одобрить (можно меньше, чем запросили).
3. **Снабжение** создаёт заявку на закупку на одобренное количество.
4. Статус закупки виден в ПТО.

Главное, что показывает прототип: **при сбое любой части процесс не теряется и не дублируется.** Заявка создаётся ровно один раз, даже если снабжение было недоступно или потерялся ответ на запрос.

## 1. Как это устроено

```
                  ┌─────────────────────┐
 ПТО ──событие──▶ │                     │ ──команда "проверь"──▶ Сметы
 Сметы ─событие─▶ │  Связующий сервис   │
 Снабжение ─соб.─▶│                     │ ──команда "создай заявку"──▶ Снабжение
                  └─────────────────────┘
                     статусы читают все
```

Приложения не обращаются друг к другу и к чужим базам данных. Всё идёт через связующий сервис.

| Сервис | Порт | Что делает |
|---|---|---|
| Связующий сервис (`hub`) | 3000 | Принимает события, ведёт процесс, отправляет команды с повторами, отдаёт статусы |
| ПТО (`pto`) | 3001 | Создаёт потребности |
| Сметы (`estimate`) | 3002 | Принимает запрос на проверку, фиксирует решение сметчика |
| Снабжение (`supply`) | 3003 | Создаёт заявки, двигает их по статусам |
| Интерфейс (`web`, React) | 5173 | Четыре панели и кнопки имитации сбоев |

У каждого сервиса своя база SQLite (папка `data/`).

## 2. Что нужно для запуска

**Вариант А: без Docker**
- Node.js 22 или новее
- npm (ставится вместе с Node.js)

Проверка:

```bash
node -v    # должно быть v22.x или выше
npm -v
```

**Вариант Б: через Docker**
- Docker Desktop (или Docker Engine с плагином Compose), запущенный

Проверка:

```bash
docker -v
docker compose version
docker info    # не должно быть ошибки подключения к демону
```

## 3. Запуск

### Шаг 1. Скачайте проект

```bash
git clone https://github.com/Amaluin/integration_test.git
cd integration_test
```

### Шаг 2а. Запуск без Docker

```bash
npm install
npm run dev
```

`npm install` занимает около минуты. `npm run dev` запускает одной командой четыре сервиса и интерфейс. В терминале появятся строки с префиксами `[hub]`, `[pto]`, `[estimate]`, `[supply]`, `[web]`.

Готово, когда в терминале видно что-то вроде `Local: http://localhost:5173/`.

### Шаг 2б. Запуск через Docker

```bash
docker compose up --build
```

Первая сборка занимает несколько минут. Готово, когда в логах нет ошибок и все пять сервисов запущены.

### Шаг 3. Откройте интерфейс

В браузере: **<http://localhost:5173>**

Должны быть четыре панели: «ПТО», «Сметный отдел», «Снабжение», «Связующий сервис». Все пустые. Справа вверху у панелей не должно быть красной метки «сервис недоступен».

### Быстрая проверка, что сервисы живы

```bash
curl http://localhost:3000/health     # {"ok":true}
curl http://localhost:3001/health
curl http://localhost:3002/health
curl http://localhost:3003/health
```

### Остановка

- Без Docker: `Ctrl+C` в терминале с `npm run dev`.
- Docker: `Ctrl+C`, затем `docker compose down`.

### Сброс данных (начать с чистого листа)

- Без Docker: остановите сервисы и удалите папку `data/`.
- Docker: `docker compose down -v`.

## 4. Пошаговое тестирование

Есть два уровня: автоматические тесты (быстро, без интерфейса) и ручные сценарии (наглядно, в браузере).

### Часть 1. Автоматические тесты

Сервисы для этого запускать не нужно: тесты поднимают весь стенд сами.

```bash
npm test
npm run typecheck
```

**Ожидаемый результат:** `Tests  9 passed (9)`; `typecheck` ничего не выводит.

Что проверяет каждый тест:

| Тест | Что доказывает |
|---|---|
| Потребность проходит ПТО → сметы → снабжение | Основной путь работает, одобрено 10,5 из 12, статусы видны в ПТО |
| Отклонённая потребность не создаёт заявку | Отказ сметчика останавливает процесс |
| Снабжение недоступно | Процесс ждёт, после восстановления заявка создаётся, и она одна |
| Заявка создана, а ответ потерян | Повтор не создаёт вторую заявку |
| Связующий сервис недоступен | Потребность сохраняется в ПТО и доходит позже |
| Событие доставлено дважды | Дубль распознаётся и не обрабатывается повторно |
| Запоздавшее событие | Статус «Поставлено» не откатывается назад на «Заказано» |
| Токены | Без токена 401; токен ПТО не может отправить событие от имени снабжения (403) |
| Ключ идемпотентности | Тот же ключ с другим содержимым отклоняется (409) |

### Часть 2. Ручные сценарии

Сначала запустите проект (раздел 3) и откройте <http://localhost:5173>. Сценарии независимы. Если хотите начать заново, сбросьте данные (раздел 3).

#### Сценарий 1. Обычный путь с частичным одобрением

1. В панели **ПТО** оставьте значения по умолчанию (объект `OBJ-0102`, арматура, 12 т) и нажмите **«Подать потребность»**.
   - Появится карточка `NEED-2026-000001` со статусом **«На проверке в сметах»**.
2. В панели **«Сметный отдел»** появится запрос `REV-2026-000001`. Замените количество с 12 на **10.5** и нажмите **«Принять решение»**.
   - Карточка станет **«Одобрено частично»**, внутри: «одобрено 10.5».
3. В панели **«Снабжение»** появится заявка `PR-2026-000001` на **10.5 т** со статусом «Создана».
   - В ПТО статус потребности: **«Заявка создана»**.
4. В «Снабжении» нажмите **«Отметить: Заказано»**.
   - В ПТО: **«Заказано»**.
5. Нажмите **«Отметить: Поставлено»**.
   - В ПТО: **«Поставлено»**.
6. В панели **«Связующий сервис»** откройте **«История»** у потребности. Там вся цепочка шагов со временем.

**Что это доказывает:** сквозной процесс работает, сметы управляют количеством, статус виден тому, кто создал потребность.

#### Сценарий 2. Отказ сметчика

1. В ПТО подайте новую потребность.
2. В «Сметном отделе» нажмите **«Отклонить»**.

**Ожидаемый результат:** в ПТО статус **«Отклонено сметами»**. В «Снабжении» новой заявки нет.

#### Сценарий 3. Снабжение недоступно

1. В панели **«Снабжение»** в строке «Имитация сбоя» нажмите **«Отключить»**. У панели появится красная метка «сервис недоступен».
2. В ПТО подайте потребность.
3. В «Сметном отделе» одобрите её (нажмите «Принять решение»).
4. Подождите 5–10 секунд и посмотрите:
   - в ПТО статус **«Одобрено, заявка создаётся»**, а не «Заявка создана»;
   - в панели «Связующий сервис» появился жёлтый блок **«Передача не завершена»** с растущим числом повторов и ошибкой `HTTP 503`;
   - в «Истории» процесса строки «Не удалось связаться со снабжением … Повтор через N с».
5. В «Снабжении» нажмите **«Работает»**.
6. Подождите до 30 секунд (паузы между повторами растут до 30 с).

**Ожидаемый результат:** жёлтый блок исчез, в «Снабжении» появилась **ровно одна** заявка, в ПТО статус «Заявка создана». Данные не потерялись.

> Если держать снабжение отключённым дольше 3–4 минут, повторы прекратятся: в жёлтом блоке появится «нужен оператор» и кнопка **«Повторить»**. Нажмите «Работает» в снабжении, затем «Повторить» — процесс продолжится.

#### Сценарий 4. Заявка создана, а ответ потерян (защита от дублей)

Это самый важный сценарий: из-за потерянного ответа система повторяет запрос, и без защиты заявок было бы две.

1. В панели **«Снабжение»** нажмите **«Потерять ответ»**.
2. В ПТО подайте потребность, в «Сметном отделе» одобрите её.
3. Подождите 5–10 секунд.

**Ожидаемый результат:**
- в «Снабжении» **одна** заявка;
- в «Истории» процесса сначала запись о неудачной попытке («Не удалось связаться со снабжением …»), затем «Снабжение создало заявку PR-…»;
- режим сбоя сам вернулся в «Работает» после первого срабатывания.

Почему так: заявка была создана, но ответ не дошёл. Связующий сервис повторил запрос с тем же ключом, снабжение узнало ключ и вернуло уже созданную заявку.

#### Сценарий 5. Сметы недоступны

1. В панели **«Сметный отдел»** нажмите **«Отключить»**.
2. В ПТО подайте потребность.

**Ожидаемый результат:** потребность остаётся «На проверке в сметах», в «Связующем сервисе» идут повторы. После нажатия **«Работает»** запрос на проверку появляется в сметах, и он один.

#### Сценарий 6. Связующий сервис недоступен

Здесь нужно остановить именно связующий сервис, остальные продолжают работать.

**Без Docker.** Остановите `npm run dev` и запустите сервисы по отдельности, в **четырёх отдельных терминалах** (в папке проекта), без связующего сервиса:

```bash
npm run pto
npm run estimate
npm run supply
npm run web
```

**Через Docker:**

```bash
docker compose stop hub
```

Дальше:

1. Откройте <http://localhost:5173>. Панель «Связующий сервис» покажет красную метку «сервис недоступен».
2. В ПТО подайте потребность.
   - Потребность сохранилась и видна в списке.
   - Над списком жёлтое сообщение **«Связующий сервис недоступен: статусы не обновляются»** и **«Не передано в связующий сервис: 1»**.
   - Статус у потребности: «Статус неизвестен».
3. Запустите связующий сервис:
   - без Docker: `npm run hub` в новом терминале;
   - Docker: `docker compose start hub`.
4. Подождите 5–10 секунд.

**Ожидаемый результат:** предупреждения исчезли, потребность получила статус «На проверке в сметах», в «Сметном отделе» появился запрос. Потребность не потерялась, хотя связующий сервис был выключен.

#### Сценарий 7. Данные в сервисах (по желанию)

Все данные доступны по HTTP:

```bash
curl http://localhost:3000/v1/flows                  # процессы и их история
curl http://localhost:3000/v1/commands/open          # незавершённые передачи
curl http://localhost:3002/api/reviews               # запросы на проверку
curl http://localhost:3003/api/procurement-requests  # заявки на закупку
```

После сценария 4 в `procurement-requests` должна быть одна заявка.

### Что считать успехом

- Автотесты: 9 из 9.
- Во всех сценариях заявок не больше одной на потребность.
- Потребности не пропадают при выключении любого из сервисов.
- Статус не откатывается назад.

## 5. Принятые решения

| Решение | Зачем |
|---|---|
| **Outbox в каждом приложении.** Бизнес-изменение и событие сохраняются одной транзакцией, отправляет их отдельный процесс | Если связующий сервис недоступен, данные не теряются: событие ждёт в своей базе |
| **Идемпотентные команды.** Ключ `Idempotency-Key` строится из номеров документов (`proc:{потребность}:v{редакция}:{проверка}`) | Повтор после сбоя возвращает ту же заявку. Ключ не случайный, поэтому после перезапуска он получится тем же |
| **Inbox у связующего сервиса.** Событие с уже виденным `id` не обрабатывается повторно | Повторная доставка безопасна |
| **Версия объекта в каждом событии.** Событие не новее уже применённого игнорируется | Запоздавшее событие не откатывает статус |
| **Повторы с нарастающей паузой** (1 → 2 → 4 … до 30 с, разброс ±20%). Ошибки данных (4xx) не повторяются, а уходят оператору | Временный сбой переживаем, ошибку в данных не повторяем впустую |
| **Одна транзакция** на «записать в inbox → сменить состояние → поставить команду» | Нет состояния «событие принято, а команда не создана» |
| **Токены у сервисов.** Источник события должен совпадать с владельцем токена | ПТО не может отправить событие от имени снабжения |
| **Состояние процесса у связующего сервиса, данные документов у их владельцев** | У каждого факта один владелец |
| **Количество сметчик указывает по каждой позиции** | Реальная смета часто одобряет только часть потребности |

Транспорт: обычный HTTP. Он есть в любом приложении, брокер сообщений не нужен.

Настройки повторов (переменные окружения связующего сервиса): `RETRY_BASE_MS` (по умолчанию 1000), `RETRY_MAX_MS` (30000), `RETRY_MAX_ATTEMPTS` (12).

## 6. Чего в прототипе нет

- **Редакций потребности и отмены.** В событиях есть `needVersion`, но повторная подача потребности игнорируется.
- **Настоящего единого входа.** Токены заданы константами в `src/shared/config.ts`. В реальной системе их выдаёт Keycloak, а пользователи входят через OIDC.
- **Прав пользователей.** Эндпоинты, которыми пользуется интерфейс (решение сметчика, смена статуса, чтение статусов), открыты.
- **PostgreSQL и нескольких экземпляров сервисов.** Здесь SQLite и по одному экземпляру. В реальной системе очередь команд берётся из PostgreSQL (`FOR UPDATE SKIP LOCKED`), схема обмена остаётся той же.
- **Сверки данных, мониторинга и оповещений.** Есть только список незавершённых передач и счётчик неотправленных событий.
- **Точной арифметики.** Количества хранятся обычными числами; для денег и точных объёмов нужны десятичные значения.

## 7. Если что-то не работает

| Симптом | Что делать |
|---|---|
| `EADDRINUSE` или «порт уже занят» | Занят порт 3000–3003 или 5173. Остановите предыдущий запуск (`Ctrl+C`) или освободите порт |
| Все панели с красной меткой «сервис недоступен» | Сервисы не запущены. Проверьте терминал с `npm run dev`; проверьте `curl http://localhost:3000/health` |
| Красная метка только у одной панели | Возможно, для неё включён режим «Отключить». Нажмите «Работает» |
| Ошибка при `npm install` на `better-sqlite3` | Нужен Node.js 22 или новее (`node -v`). На Windows может понадобиться установить «Build Tools for Visual Studio» |
| `docker compose` пишет «cannot connect to the Docker daemon» | Запустите Docker Desktop и дождитесь, пока он полностью загрузится |
| Страница открывается, но данных нет после перезапуска | Данные хранятся в `data/` (или в томах Docker). Если папку удалили, всё начинается заново |
| В интерфейсе всплыло окно с ошибкой | Это ответ сервиса на недопустимое действие (например, количество больше запрошенного). Текст ошибки в окне |
| Нужно начать с нуля | Раздел 3, «Сброс данных» |

## 8. Структура проекта

```
src/shared/     общее: outbox, имитация сбоев, типы событий, авторизация
src/hub/        связующий сервис: приём событий, ведение процесса, отправка команд
src/pto/        приложение ПТО (заглушка)
src/estimate/   приложение смет (заглушка)
src/supply/     приложение снабжения (заглушка)
web/            интерфейс на React (Vite)
tests/          автоматические тесты (Vitest)
Dockerfile, docker-compose.yml
```

Стек: TypeScript, Node.js, Fastify, SQLite (better-sqlite3), React, Vite, Vitest.
